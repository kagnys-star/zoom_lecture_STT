# 다른 프로젝트에 전달할 180초 무음 강의 경계 구현 프롬프트

아래 내용을 그대로 복사해 대상 프로젝트의 코드 작업 에이전트에게 전달하면 된다. 클래스와 파일
이름은 ZoomCaption 기준이므로, 대상 프로젝트의 실제 구조를 먼저 찾아 대응시키도록 작성했다.

---

이 프로젝트의 오디오 캡처, 실시간 전사, Whisper 재전사, 저장소, 화면 표시 경로를 먼저 끝까지
추적한 뒤 아래 동작을 구현해라. 기존 사용자 변경사항은 보존하고, 수정하는 모든 코드에는 **왜 이
동작이 필요한지와 어떤 경쟁 상태를 막는지 설명하는 자세한 주석**을 작성해라. `x`, `tmp`, `flag`
같은 축약 이름 대신 역할이 드러나는 의미 있는 변수명과 메서드명을 사용해라.

## 목표 동작

실시간 전사기(transcriber)와 Whisper는 독립적으로 계속 실행한다. Whisper는 실시간 자막 엔진이
아니라 약 60~90초 뒤에 더 정확한 문장으로 복기하는 엔진이다. 마지막 유효 소리 이후 **180초
연속 무음**이 확인되면 녹음을 멈추지 말고 현재 강의 단위만 마무리한다. 이후 소리가 돌아오면 두
전사기는 같은 인스턴스 또는 정상적인 기존 수명주기로 계속 처리해야 한다.

## 구현 요구사항

1. 새로 증가시키는 무음 카운터를 만들지 마라. 기존에 마지막 비무음 샘플을 받은 절대 시각
   (`lastNonSilentAt` 또는 같은 의미의 값)이 있으면 재사용하고, 현재 시각과의 차이로 무음 시간을
   계산해라. 시스템 캡처와 관리자 파일 되먹임이 있다면 둘 다 같은 오디오 활동 시계를 갱신하게
   해라.

2. 짧은 캡처 이상 경고 기준과 강의 종료 기준을 분리해라. 캡처 경고가 30초라면 유지하고, 강의
   경계는 별도 상수 `180`초로 둬라. 녹음 시작 뒤 유효 소리를 한 번도 받지 않았다면 강의 종료를
   만들지 마라.

3. 같은 무음 구간을 식별할 수 있도록 작업 시작 시 `lastNonSilentAt` 스냅샷을 잡아라. Whisper를
   기다린 뒤 현재 `lastNonSilentAt`이 스냅샷과 같은지, 무음이 여전히 180초 이상인지 다시 확인해라.
   중간에 소리가 한 번이라도 들어왔다면 오래된 작업은 아무 상태도 지우지 않고 종료해야 한다.

4. 같은 무음 구간에서는 경계를 한 번만 처리하고, 소리가 돌아온 뒤 다음 180초 무음에 다시
   처리할 수 있게 재무장해라. 비동기 작업에는 녹음 세대 ID와 작업 ID를 두어 stop/start 뒤의
   오래된 작업이 새 세션을 변경하지 못하게 해라. stop은 경계 작업을 취소하고 완료를 기다린 뒤
   문장 버퍼를 최종 정리해라.

5. 180초 경계 시 Whisper 워커를 종료하거나 seal하지 마라. 먼저 AudioArchive에서 진행 중인 VAD
   분할이 끝났는지 확인하고, 아직 `pending`에만 있는 2초 이상의 자투리 오디오를 파일을 닫지 않은
   채 `onChunk`로 방출해라. 시스템 탭은 무음 PCM을 계속 보내지만 관리자 되먹임이나 입력 중단은
   마지막 버퍼 뒤에 프레임을 더 주지 않아, 이 처리가 없으면 마지막 발화가 Whisper 큐에 들어가지
   못할 수 있다. 그다음 Whisper의 현재 큐와 실행 중 작업이 모두 끝날 때까지만 제한 시간 동안
   기다리는 `waitUntilIdle` 계열 API를 추가해라. 큐가 비어 있어도 현재 프로세스가 실행 중일 수
   있으므로 `queue.isEmpty && !draining` 같은 두 조건을 함께 확인해라. 제한 시간 안에 어느 한쪽이라도
   안전하게 끝나지 않으면 문장 꼬리를 자르지 말고 다음 감시 주기에 재시도해라.

6. Whisper가 유휴가 되고 같은 무음이 확인되면 다음 순서로 처리해라.

   - 구두점이 없어 문장 재구성기에 남은 pending 조각을 한 문장으로 확정한다.
   - 오른쪽 문맥을 기다리며 숨겨진 마지막 문장들의 문단 번호를 현재 정보로 확정한다.
   - 다음 Whisper 문장 하나가 이전 문단에 붙지 않고 새 문단에서 시작하도록 1회성 상태를 둔다.
   - 이번 녹음 구간의 마지막 영속 문장 뒤에 구조화된 강의 종료 경계를 붙인다.
   - 상태 저장과 화면 이벤트 전파를 수행한다.

7. 강의 종료 문구를 실제 전사 문자열에 이어 붙이지 마라. 영속 문장 모델에 Optional 필드
   `boundaryAfter`를 추가하고 값은 `lectureEnded`처럼 구조화해라. Optional이어야 기존 JSON에 해당
   키가 없어도 디코딩된다. 화면과 Markdown에서는 마지막 문장 다음에 “강의 종료”를 표시하되,
   SRT·검색·요약·교정에 입력되는 실제 음성 텍스트에는 포함하지 마라.

8. 이번 녹음 구간에 Whisper 문장이 있으면 마지막 Whisper 문장에 경계를 붙이고, Whisper 결과가
   하나도 없으면 마지막 실시간 확정 문장에 붙여라. 이어 적기 시작 오프셋보다 이전 문장은 후보로
   고르지 마라. 그래야 새 구간에서 아무 말도 하지 않았을 때 과거 강의 문장이 변경되지 않는다.

9. `volatile` 이벤트 형식에는 start/end/revision을 추가하지 마라. 이 값은 현재 임시 문구 하나를
   교체하는 비영속 UI 상태이므로 이번 해결에 스키마 확장이 필요하지 않다. 실시간 final 또는 새
   Whisper 문장이 도착했다는 이유만으로 volatile을 즉시 비우지도 마라. 오래된 final/Whisper
   콜백이 새 volatile을 지울 수 있다. 180초 경계를 확정한 뒤 같은 무음이 여전히 유지되는지 한 번
   더 확인하고, 그때만 기존 형식 그대로 빈 문자열 volatile 이벤트를 한 번 보내라. 경계 확정 도중
   소리가 재개됐다면 문장 경계는 유지하되 현재 volatile은 보존해라.

10. 경계 필드를 전체 상태 API, 실시간 이벤트, 재연결 병합, 최초 화면 렌더, Markdown 저장까지
    빠짐없이 전달해라. 화면의 강의 종료 표식은 전사 텍스트 DOM 바깥에 렌더해 편집·검색 대상이
    되지 않게 해라. 이벤트를 놓쳐도 다음 상태 스냅샷 병합으로 복구되어야 한다.

## 검증 기준

- 과거 저장 파일에 `boundaryAfter`가 없어도 정상적으로 열린다.
- 발화 뒤 179초 무음에서는 경계가 생기지 않고, 180초 이상에서 한 번만 생긴다.
- Whisper pending 문장과 문단 꼬리가 다음 발화를 기다리지 않고 표시된다.
- 180초 처리 후 녹음, 실시간 전사기, Whisper 워커는 계속 살아 있다.
- 소리가 재개되면 다음 Whisper 문장은 새 문단으로 시작한다.
- Whisper 대기 중 소리가 재개되면 오래된 작업이 새 volatile을 지우지 않는다.
- 같은 무음에서 감시 타이머가 여러 번 실행돼도 종료 표식이 중복되지 않는다.
- 관리자 파일 되먹임도 실제 시스템 캡처와 같은 오디오 활동 시계를 사용한다.
- stop/start 뒤 이전 비동기 작업이 새 세션을 변경하지 않는다.
- 전체 빌드와 기존 테스트를 실행하고, 변경 파일 diff에서 축약 변수명과 설명 없는 상태 변경이
  없는지 다시 검토한다.

구현을 마친 뒤에는 변경 파일, 상태 전이 순서, 동시성 방어 방식, 실행한 검증과 남은 한계를
구체적으로 보고해라.
