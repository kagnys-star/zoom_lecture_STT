# 1분 이상 무음 뒤 Whisper가 멈춘 것처럼 보이는 현상 분석

- 분석일: 2026-09-08
- 분석 대상: ZoomCaption의 `AudioArchive → WhisperLive → Whisper → Store → Web UI` 경로
- 결론 상태: 코드 및 운영 로그로 원인 경로 확인. 이번 작업에서는 코드 변경 없이 해결 설계만 제시한다.

## 1. 결론

이 현상의 주원인은 **Whisper 프로세스가 무음 때문에 실제로 정지하는 것**이 아니다.

현재 구현은 무음 조각을 약 30초마다 정상적으로 잘라 처리한 뒤, 환각을 막기 위해
Whisper에 보내지 않고 폐기한다. 문제는 이 정상적인 무음 처리가 화면에는 아무 이벤트도
남기지 않는다는 데 있다. 화면은 "Whisper가 어디까지 처리했는가"를 별도 상태로 받지 않고,
마지막으로 표시된 Whisper 문장의 끝 시각만 처리 진척도로 간주한다. 따라서 무음이 계속되면
Whisper 처리 시각이 화면에서 멈춘 것처럼 보이고, 아래쪽 SpeechTranscriber 자막은 제거 계기를
잃고 남는다.

여기에 다음 두 동작이 겹쳐 증상이 더 확실해진다.

1. SpeechTranscriber의 휘발성 문구는 서버 내부에서는 확정 결과가 나올 때 비워지지만,
   브라우저로 빈 문자열 이벤트를 보내지 않는다. 브라우저는 다음 Whisper 문장이 표시될 때만
   이 문구를 비우므로, 무음 중에는 `받아쓰는 중` 문구가 오래 남을 수 있다.
2. Whisper의 마지막 미완성 문장과 문단 판정 대기 중인 마지막 세 문장은 다음 Whisper 결과가
   와야 화면에 풀린다. 긴 무음에서는 다음 결과가 없으므로 실제로 처리된 마지막 발화도 화면에
   나타나지 않아 "Whisper가 멈췄다"는 인상을 준다.

따라서 정확한 분류는 다음과 같다.

- 오디오 수집: 계속 동작한다.
- 무음 조각 생성과 폐기: 계속 동작한다.
- SpeechTranscriber: Whisper와 독립적으로 계속 동작한다.
- Whisper 실행: 무음 조각에는 의도적으로 실행하지 않는다.
- Whisper 화면 갱신: 새 텍스트가 없으므로 멈춘다.
- 실시간 자막 정리: 다음 Whisper 텍스트 이벤트에 잘못 의존하므로 남는다.

다만 VAD 보조 프로세스와 `whisper-cli` 자체에 실행 시간 상한이 없다는 별도의 결함도 있다.
이 두 프로세스 중 하나가 실제로 멈추면 전체 Whisper 경로가 영구 고착될 수 있다. 운영 로그에는
이번 증상이 그 고착이었다는 증거가 없지만, 같은 화면 증상을 만드는 잠재 경로이므로 함께 막아야 한다.

## 2. 현재 처리 흐름

### 2.1 오디오와 Whisper의 의도된 지연

`AudioArchive`는 다음 값을 사용한다.

- 목표 조각 길이: 30초
- Whisper 교체 지연: 60초
- 최초 조각 생성 조건: 90초의 오디오가 쌓였을 때

90초가 쌓이면 앞쪽 약 30초를 떼어 Whisper 후보로 만들고, 뒤쪽 약 60초는 계속 보관한다.
SpeechTranscriber는 이 과정과 무관하게 같은 입력 버퍼를 즉시 받는다.

### 2.2 무음에서 실제로 일어나는 일

조각의 최대 진폭이 Int16 기준 250 이하이면 `flushChunk`가 조각을 Whisper에 넘기지 않고
바로 반환한다. 이 판정은 무음 환각을 막기 위한 정상 동작이다.

반환하기 전에 이미 다음 상태 갱신은 끝난다.

- 처리한 샘플을 `pending`에서 제거한다.
- `emitted`를 다음 시각으로 이동한다.
- `chunkIndex`를 증가시킨다.
- `defer`에서 `cutting = false`로 돌린다.

즉, 무음 조각을 버렸다는 이유만으로 다음 조각 생성이 막히지는 않는다. 오디오가 계속 들어오면
대략 30초 뒤 다시 90초 조건을 만족해 다음 조각을 처리한다.

### 2.3 화면이 사용하는 잘못된 대리 상태

브라우저에는 실제 Whisper 처리 완료 시각이 없다. 대신 `whisperCoverEnd`라는 값을 두고,
화면에 새 Whisper 문장이 추가될 때 그 문장의 `end`로만 값을 증가시킨다.

따라서 다음 경우에는 백엔드가 정상이어도 `whisperCoverEnd`가 움직이지 않는다.

- 무음 조각이 진폭 필터에서 폐기된 경우
- `whisper-cli`가 성공했지만 텍스트가 빈 경우
- 문장 재구성기가 마지막 미완성 문장을 보류한 경우
- 문단화가 뒤쪽 문맥 세 문장을 기다리며 결과를 보류한 경우
- Whisper 실행 또는 JSON 파싱이 실패한 경우

아래쪽 실시간 확정 자막을 지우는 `trimFast`도 이 값이 늘거나 새 실시간 문장이 들어올 때만
실행된다. 코드에 180초 안전 구간이 있지만 벽시계 타이머가 아니다. 새 이벤트가 전혀 없으면
계산 자체가 다시 실행되지 않으므로 마지막 실시간 줄은 180초가 지나도 계속 남을 수 있다.

## 3. 직접 원인

### 원인 A — 무음 처리 완료 시각이 소실됨

`AudioArchive.flushChunk`는 무음이면 로그만 남기고 `onChunk`를 호출하지 않는다. 따라서
`WhisperLive`는 그 구간을 큐에 넣지 않고, 완료 진행 이벤트도 발생하지 않는다.

무음을 Whisper에 넣지 않는 정책은 맞다. 문제는 "텍스트가 없다"와 "아직 처리하지 않았다"를
같은 상태로 표현하는 것이다. 현재 화면은 둘을 구분할 수 없다.

### 원인 B — 실시간 휘발성 문구의 소유권이 Whisper에 묶임

`TranscriptStore.appendFinal`은 내부 `volatile[track]` 값을 빈 문자열로 바꾸지만,
`onChange(.volatile(track, ""))`를 호출하지 않는다. 브라우저의 `liveText`는 이 변경을 모른다.

현재 브라우저가 휘발성 문구를 비우는 주요 경로는 새 Whisper 문장을 표시하는
`addSegment(..., fresh: true)`이다. 무음 중에는 새 Whisper 문장이 없으므로 마지막 휘발성
SpeechTranscriber 문구가 계속 남는다. 실시간 자막의 수명주기를 60~90초 뒤의 별도 엔진이
간접 관리하는 구조가 직접적인 설계 오류다.

### 원인 C — Whisper의 마지막 결과를 다음 발화까지 보류함

`SentenceReconstructor`는 구두점을 만나지 못한 마지막 조각을 다음 Whisper 줄까지 보관한다.
또한 문단화는 오른쪽 문맥을 확보하려고 마지막 `Paragraph.windowRadius`, 현재 세 문장을
화면에 보내지 않는다.

정지 버튼을 누르면 `finalize()`와 `finalizeParagraphs()`가 이 꼬리를 풀지만, 녹음이 계속된 채
무음만 길어지는 경우에는 같은 처리가 없다. 그래서 마지막 실제 발화가 이미 Whisper를 거쳤어도
위쪽 정식 기록에 나타나지 않을 수 있다.

## 4. 운영 로그 근거

운영 로그는 "무음이 `cutting`을 영구 고착시킨다"는 가설을 반박한다.

### 4.1 장시간 무음에서도 조각 생성은 계속됨

2026-08-27 로그에는 09:26:45부터 10:04:45까지 약 30초 간격으로 무음 조각 폐기 로그가
77회 연속 기록되어 있다. `cutting`이 한 번이라도 `true`에 고착됐다면 두 번째 로그부터 나올
수 없으므로, 오디오 축적·조각 생성·VAD 경계 탐색·상태 복구가 계속 동작했다는 증거다.

### 4.2 2분 30초 이상 무음 뒤 Whisper 실행이 재개됨

2026-09-07 로그에는 다음 순서가 남아 있다.

- 14:04:40 ~ 14:07:10: 무음 조각 여섯 개를 연속 폐기
- 14:07:45: `chunk_0010.wav` Whisper 실행
- 14:08:15 이후: `chunk_0011.wav`, `chunk_0012.wav` 등 계속 실행

즉, 실제 백엔드는 긴 무음 뒤 유효한 소리가 다시 들어오자 자동으로 재개됐다.

### 4.3 현재 로그의 한계

현재 로그는 `whisper 실행` 시작과 오류만 남기고 정상 완료 시각, 처리 구간의 끝 시각,
큐 깊이, 실행 중인 프로세스의 경과 시간을 남기지 않는다. 따라서 사용자가 본 정확한 시각을
모르면 화면 정체와 실제 프로세스 고착을 사후 로그만으로 100% 구별할 수 없다.

## 5. 해결 설계

### 5.1 최우선 — 상태를 텍스트와 분리한다

서버에 단조 증가하는 처리 상태를 추가한다.

- `capturedThrough`: 오디오가 실제로 들어온 마지막 세션 시각
- `archiveResolvedThrough`: 조각으로 잘라 무음 여부까지 판정한 마지막 시각
- `whisperResolvedThrough`: Whisper 실행까지 성공 또는 정책적으로 완료한 마지막 시각
- `whisperTextThrough`: 실제 Whisper 텍스트가 존재하는 마지막 시각

무음 조각도 `archiveResolvedThrough`를 전진시키고 `whisperCoverage` 이벤트를 내보내야 한다.
유효 조각은 `WhisperLive`가 전사를 끝낸 뒤 `whisperResolvedThrough`를 전진시킨다. 이렇게 하면
화면과 진단 API가 다음 세 상태를 구분할 수 있다.

- 정상 무음: 처리 시각은 전진하지만 텍스트 시각은 그대로
- Whisper 지연: 큐가 존재하고 처리 시각이 잠시 정지
- 실제 고착: 입력 시각은 전진하는데 처리 시각이 제한 시간을 넘겨 정지

Whisper 실행 실패 구간은 처리 완료로 위장하지 말고 `failed` 상태로 표시해야 한다. 이때 해당
구간의 SpeechTranscriber 확정 기록은 대체 자료로 남기는 편이 안전하다.

### 5.2 최우선 — volatile은 스키마를 늘리지 않고 180초 경계에서만 지운다

`volatile`에 start/end/revision을 추가하지 않는다. 이 값은 저장 문장이 아니라 현재 받아쓰는 중인
문구 한 개를 교체하는 UI 상태이므로, 이번 문제를 해결하는 데 새 식별자나 시간축이 필요하지 않다.

SpeechTranscriber의 final 직후 즉시 빈 `volatile`을 방송하는 방식도 사용하지 않는다. final과 다음
volatile 콜백의 순서가 엇갈리면 오래된 final이 새로 받아쓰는 문구를 지울 수 있기 때문이다. 대신
180초 무음 경계가 비동기 Whisper 대기 뒤에도 같은 `lastNonSilentAt`을 가리키는지 재검증하고,
그때만 빈 `volatile` 이벤트를 한 번 보낸다. 화면이 새 Whisper 문장 도착에 기대어 임시 문구를
지우던 기존 결합도 제거한다.

### 5.3 3분 무음을 하나의 명시적 강의 경계로 처리한다

연속 무음이 180초를 넘으면 녹음을 종료하지 않은 채 표시용 꼬리만 확정한다.

- `SentenceReconstructor.flushPendingForLectureBoundary()`로 구두점 없는 마지막 문장을 내보낸다.
- `TranscriptStore.finalizeParagraphsForLectureBoundary()`로 오른쪽 문맥을 기다리는 문장을 표시한다.
- 다음 유효 발화는 새 문단으로 시작하도록 1회성 경계 상태를 둔다.
- 마지막 영속 문장에는 Optional `boundaryAfter: lectureEnded`를 붙인다.

강의 종료 문구는 `Segment.text`에 합치지 않는다. 화면과 Markdown은 구조화된 경계를 별도 표시하고,
SRT·검색·요약에 쓰는 실제 발화 텍스트는 오염시키지 않는다. 기존 저장 파일에는 이 키가 없으므로
Optional 필드로 추가해 하위 호환성을 유지한다. 중요한 점은 기존 `finalize()`처럼 객체를 닫지 않는
것이다. 일시 정리만 하고 이후 발화는 계속 받을 수 있어야 한다.

### 5.4 실시간 확정 기록을 숨기는 정책을 명확히 한다

무음으로 판정한 구간에 SpeechTranscriber 확정 문장이 존재할 수 있다. 이때 선택지는 둘이다.

1. 단순 정책: `whisperResolvedThrough` 이전 실시간 줄을 모두 숨긴다.
2. 안전 정책: 같은 구간에 Whisper 대체 문장이 있는 실시간 줄만 숨기고, 대체 문장이 없으면
   `Whisper 결과 없음 · 실시간 대체` 표식을 붙여 남긴다.

두 번째 정책을 권장한다. 진폭 필터가 매우 조용한 실제 발화를 무음으로 오판하거나 Whisper가
실패한 경우에도 사용자가 내용을 잃지 않는다. "실시간 줄이 남는다"를 무조건 오류로 취급하지
않고, 남은 이유를 명시하는 방식이다.

### 5.5 실제 프로세스 고착을 막는 감시 장치를 추가한다

운영 로그에서 무음이 직접 고착을 만든 증거는 없지만, 현재 코드는 두 곳에서 무한 대기가 가능하다.

#### VAD 경계 탐색

`VADBoundary.speechSegments`는 외부 프로세스의 stdout 종료와 프로세스 종료를 제한 없이 기다린다.
이 프로세스가 멈추면 `AudioArchive.cutting`이 계속 `true`여서 이후 조각을 만들 수 없다.

권장 동작:

- 45초 탐색 WAV의 정상 실측 시간보다 충분히 큰 10~15초 제한을 둔다.
- 초과 시 프로세스를 종료한다.
- 해당 조각은 정확히 30초 지점에서 자르는 기존 폴백을 사용한다.
- 제한 초과, 파일명, 실행 시간, 폴백 여부를 로그와 상태 이벤트로 남긴다.

#### Whisper 전사

`Whisper.transcribe`도 `whisper-cli` 종료를 제한 없이 기다린다. 한 작업이 멈추면
`WhisperLive.draining`이 계속 `true`이고 이후 조각은 큐에만 쌓인다.

권장 동작:

- 30초 조각의 정상 실측 시간보다 넉넉한 45~60초 제한을 둔다.
- 초과 시 실행 중인 프로세스를 종료하고 해당 조각을 실패로 기록한다.
- 큐 드레인은 다음 조각으로 계속 진행한다.
- 실패 구간의 SpeechTranscriber 기록은 숨기지 않는다.
- 같은 조각을 자동 재시도한다면 최대 한 번만 하고, VAD를 끄는 재시도는 환각 위험을 별도
  표시한 경우에만 사용한다.

프로세스 종료와 타임아웃 태스크가 동시에 완료될 수 있으므로 continuation을 두 번 resume하지
않는 단일 완료 게이트가 필요하다. 종료 요청 후 짧은 유예를 두고 여전히 살아 있을 때 강제 종료하는
단계도 포함해야 한다.

## 6. 관리자 모드 재현 및 검증 계획

### 6.1 시험 음원

다음 패턴의 16kHz mono WAV를 사용한다.

- 0:00 ~ 2:00: 연속 발화
- 2:00 ~ 4:00: 완전 무음
- 4:00 ~ 6:00: 연속 발화

관리자 모드를 별도 포트와 임시 저장 폴더로 실행하고 `/api/admin/feed`로 되먹인다. 배속은 먼저
1배로 기준 결과를 만들고, 상태 전이 검증은 4~8배로 반복한다. 실사용 세션과 섞이지 않도록
반드시 `--admin --dir <임시 폴더> --port <별도 포트> --no-open` 조합을 사용한다.

### 6.2 수집할 관측값

- 각 조각의 `[start, end]`, peak, 무음 판정
- VAD 시작·완료·실행 시간
- Whisper 큐 진입·시작·완료·실패·실행 시간
- `capturedThrough`, `archiveResolvedThrough`, `whisperResolvedThrough`, `whisperTextThrough`
- SpeechTranscriber final/volatile clear 이벤트
- 문장 재구성 대기 개수와 문단 대기 개수

### 6.3 통과 조건

- 무음 중에도 `archiveResolvedThrough`가 약 30초 단위로 증가한다.
- 60초 연속 무음 뒤 휘발성 `받아쓰는 중` 문구가 남지 않는다.
- 무음 직전 Whisper 문장과 문단이 다음 발화를 기다리지 않고 표시된다.
- 두 번째 발화가 들어오면 Whisper 큐가 자동으로 다시 움직인다.
- 첫 번째 발화와 두 번째 발화 사이에 존재하지 않는 Whisper 문장이 생성되지 않는다.
- Whisper 실패 구간에 실시간 확정 기록이 있으면 화면과 저장 파일에서 보존된다.
- VAD 또는 Whisper 시험 프로세스를 의도적으로 지연시켜도 제한 시간 뒤 다음 조각으로 진행한다.

## 7. 구현 우선순위

1. **P1: 180초 무음 시 문장·문단 꼬리 확정과 구조화된 강의 경계 저장** — Whisper가 멈춘
   것처럼 보이는 핵심 표시 문제를 해결한다.
2. **P1: 같은 무음 재검증 뒤 휘발성 자막 clear** — 새 발화의 volatile을 지우지 않으면서 남아
   있는 SpeechTranscriber 임시 문구를 정리한다.
3. **P1: 처리 watermark와 텍스트 watermark 분리** — 정상 무음, 처리 지연, 실제 고착을 화면과
   진단에서 구별한다.
4. **P1: VAD와 whisper-cli 타임아웃 및 다음 조각 계속 처리** — 잠재적인 영구 고착을 차단한다.
5. **P2: 관리자 되먹임 회귀 시험과 조각 수명주기 로그** — 같은 문제가 재발했을 때 원인을
   즉시 판별할 수 있게 한다.

## 8. 수정 범위 제안

- `AudioArchive.swift`: 무음 포함 조각 판정 결과와 처리 끝 시각 콜백 추가
- `VADBoundary.swift`: 외부 프로세스 시간 제한과 폴백 결과 기록
- `Whisper.swift`: 전사 프로세스 시간 제한과 구조화된 성공/실패 결과
- `WhisperLive.swift`: 작업의 끝 시각·상태를 포함한 진행 이벤트, 실패 후 큐 계속 처리
- `SentenceReconstructor.swift`: 객체를 닫지 않는 lecture-boundary flush 추가
- `Store.swift`: 경계 시 volatile clear, 문단 꼬리 확정, Optional 강의 종료 표식 추가
- `ZoomCaptionApp.swift`: 기존 마지막 유효 소리 시각으로 180초 경계와 재검증 연결
- `WebUI+Script.swift`: 구조화된 강의 종료 표식 표시와 Whisper 도착 기반 volatile clear 제거

## 9. 최종 판단

현재 현상은 **독립 실행되는 두 전사기 중 Whisper만 죽은 것**으로 단정하면 안 된다. 운영 로그상
Whisper 조각 파이프라인은 장시간 무음 중에도 계속 전진했고, 2분 30초 이상의 무음 뒤에도 다시
실행됐다. 확인된 주원인은 무음에서는 텍스트가 없다는 정상 상태를 화면이 처리 정지로 오해하고,
실시간 임시 표시와 Whisper의 보류된 꼬리를 다음 Whisper 텍스트에 의존해 정리하는 상태 모델이다.

해결의 핵심은 Whisper에 무음을 억지로 넣는 것이 아니라, **처리 진척도와 텍스트 생성 여부를
분리하고, 3분 무음을 표시 경계로 사용하며, 같은 무음이 유지될 때만 임시 상태를 정리하는 것**이다.
그 위에 외부 프로세스 타임아웃을 추가하면 화면상의 정체와 실제 고착을 모두 해결할 수 있다.

## 10. 구현 후 관리자 통합 시험

2026-09-08에 격리 포트와 임시 저장 폴더에서 5초 합성 음성 파일을 관리자 되먹임으로 넣어 실제
180초를 기다렸다.

- 파일 종료 뒤 `framesSeen`은 100,527에서 멈췄지만 `silenceSeconds`는 71초, 138초 순으로 계속
  증가했다. 별도 누적 타이머가 아니라 마지막 유효 소리 시각을 기준으로 계산하는 경로가 확인됐다.
- 첫 시험에서는 관리자 파일 입력이 끝난 뒤 무음 PCM도 더 보내지 않아 5초 오디오가
  `AudioArchive.pending`에 남는 차이를 발견했다. 이에 파일을 닫지 않고 pending만 방출하는
  `flushPendingForLectureBoundary`를 추가했다.
- 보완 뒤에는 180초를 넘은 첫 20초 감시 틱에서 `chunk_0000.wav` Whisper 실행이 시작됐고,
  마지막 Whisper 문장에 `boundaryAfter: lectureEnded`가 저장됐다. 실제 발생 시각은 임계값 뒤 약
  12초였으며 이는 20초 감시 주기의 정상적인 지연 범위다.
- 경계 뒤에도 상태 API는 `running: true`였다. 같은 실행에 음성을 다시 넣자 프레임 수가
  201,054로 증가하고 무음 시간은 약 5초로 돌아왔다.
- 정지 후 결과에서 경계 전 두 문장은 문단 1, 재개 뒤 두 문장은 문단 2였다. 다음 문장 ID를
  기억하는 문단 경계가 실제로 적용됐다.
- `session.json`에는 `lectureEnded`, `transcript.md`에는 `강의 종료`가 기록됐고,
  `transcript.srt`에는 어느 표식도 들어가지 않았다.
- 같은 무음 구간의 후속 감시 틱에서는 종료 로그나 표식이 중복 생성되지 않았다.
